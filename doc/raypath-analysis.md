## 1. 功能全景

「光路分析」这个词覆盖的是一族用户问题，它们共享一个对象（光线从光源到相机所经过的
完整光路），但要回答的问题、需要的数据形状、以及成本，彼此差别很大：

- **这道弧是谁做的？** —— 天空某处的光由哪些光路贡献、各占多少。
- **关掉它，下面压着什么？** —— 在普通渲染图上把某个晶体 / 某条光路的贡献即时去掉，
  看剩下的画面。
- **光在晶体里实际怎么走？每一段剩多少能量？** —— 点一条光路（如 `3-5-6-7`），看到它在晶体
  里的真实轨迹，以及能量沿路径逐段衰减的比例。

前两个问题是内测用户最早提出的需求拆开后的两半，第三个是后来的用户诉求。状态总表：

| 方向 | 状态 | 依赖的地基能力 | 详见 |
|---|---|---|---|
| **(i) 识别**：列出一个区域里各光路成分与占比 | ✅ 已交付（PR #347） | 完整链 id、专用分析运行、CPU 路 | §3；[`raypath-analysis-panel.md`](raypath-analysis-panel.md) |
| **(ii) 剥离**：在渲染图上即时开关某个桶 | ⏸ 搁置（owner 2026-08-26 裁定） | 每桶真实辐射量（内存墙所在） | §4 |
| **选定光路后的三功能**：① 光路详情（fiber） ② 单光路全天图（产品形态见 §5.1.8） ③ 预设点 | 🔜 规划中（升级为第二产品核心，见 §5.1 产品形态；①一期落地，②与③的大部分随二期，见 §5.1.8「两期」） | 一期：晶体几何 + Lumice C++ 单光路反解 / fiber 行走（parity 对照 LI，见 §5.1.6「仓库定位」）；二期：S² `D_P` 场（LI Phase II） | §5.1 |

## 2. 拆分决策：(i) 识别 vs (ii) 剥离

内测用户最初提的是「在普通仿真图上动态开关某个晶体 / 某个 filter 对应的弧」。
拆开看是两个需求，成本落在完全不同的地方：

| | 用户要回答的问题 | 需要什么 | 成本量级 |
|---|---|---|---|
| **(i) 识别** | 「这道弧是谁做的」 | 各贡献者的**份额**（最初设想是每像素一个主贡献者 id） | 与桶数无关（一张 uint16 id 图在 1024² 下约 2 MB；已交付形态更小，见 §3） |
| **(ii) 剥离** | 「关掉这道亮的，看下面压着什么」 | 每桶**真实辐射量** | 与桶数**线性**：XYZ 每桶在 1024² 下约 24 MB（含快照影子一份） |

**为什么先做 (i)**：

1. (i) 的成本与桶数无关，(ii) 的成本随桶数线性增长并且撞墙（§4.1）。
2. 「开关某条弧」是用户提出的**解法**，「知道这里有什么、各占多少」才可能是他们的**目的**。
   两者不一定是同一件事，而它们的成本差一个量级。按目的做，(i) 就够回答大半问题；
   (ii) 剩下的只是「是否还需要**即时**开关」这一窄问题（§4.4）。
3. 在 (i) 之上顺带就有一条 (ii) 的部分解：列表行 →「排除此光路」→ 生成 filter → 重跑。
   零新增存储，代价是等一次重跑而不是即时。

## 3. (i) 已交付的形态

(i) 没有按最初设想做成「每像素一张主贡献者 id 图」，而是做成了第三种形态：
一个独立的光路分析面板，带自己的 Analyze 按钮，点击后发起一轮**专用运行**——
这轮运行**不渲染**，只按「完整光路」（从光源到相机，跨多次散射层，按对称性逐段约化）
聚合能量，按能量降序列出。分析区域三档：全天 / 画幅内 / 以某个方向为中心的锥形邻域。

它绕开内存墙的方式可以拆成两处：(ii) 的成本是 N（按光路分桶）× W×H（每桶一张图），
而「同一次运行既要出渲染图又要出分解」把这两个维度焊在一起。**专用运行**拆掉了与渲染的
耦合，**统计量而非图**拆掉了像素维度，于是内存只随「有多少条不同的光路」增长，并且已被
有界记录压成常量上界（`raypath-analysis-panel.md` §3.6）。

它也是 §4.2 路线 E「不存、需要时算回来」的泛化：E 是同一个 consumer 逐桶重跑，这里是换一个
consumer（按链 id 聚合，而不是按像素渲染）跑一次，一次拿到所有桶的排序。

v1 的四条裁决（CPU 路且显式声明、完整链、锥形 ROI、按总能量降序）、诚实边界与后续修复，
都在 [`raypath-analysis-panel.md`](raypath-analysis-panel.md)（§2 裁决、§6 诚实边界）；
用户侧怎么用见 [用户手册](user-manual/06-raypath-analysis_zh.md)。本文不复述。

## 4. (ii) 剥离：为什么搁置

⛔ **(ii) 已于 2026-08-26 由 owner 决定搁置，不是待办。** 搁置理由：五条实现路线（§4.2）各有
优点但找不到好的权衡点；top-K 看起来最均衡，但 owner 预判实际使用中用户会要求很大的 K，
内存压力仍在。更关键的是，卡住决策的不确定度**已经不是技术性的**：剩下的两个问题——用户要
多大的 K、有了光路分析之后还要不要单独开关——只有用户能答，再做多少轮设计也答不出来。

本节保留的是重新推导代价很高的部分：已核实的规模事实、五条路线的关键约束、被否决的方向。

### 4.1 两条已核实的规模事实（⛔ 勿凭印象重推）

模拟分辨率档位为 512 / 1024 / 2048 / 4096，GUI 默认 1024（`kSimResolutions`，
`src/gui/gui_state.hpp`）。每桶成本 = 累加通道 + 快照影子各一份：

| 每桶 | 1024² | 4096² |
|---|---|---|
| **Y-only**（今天 Colors 面板的形态） | 8 MB | 128 MB |
| **XYZ**（剥离需要的真实颜色） | 24 MB | 384 MB |

1. **内存墙不是 XYZ 引入的，Y-only 今天就撞得上。** 40 个晶体 × 4096 分辨率下，
   现有 Y-only 形态就是约 5 GB；XYZ 只是把同一堵墙往前挪 3 倍。真正的成本源是
   **「为每个桶预先分配一条全分辨率通道」这个形态**，不是通道里装几个分量。
   ⇒「保住 Y-only 就能支撑极端用法」不成立——那个用法今天也不成立，只是还没有人同时开几十个
   color class。
2. **「几百个 filter 逐个开关」在撞内存之前先撞位预算。** component 掩码是 64 位
   （`ComponentTable::kMaxBits = 64`），超出后溢出项拿不到位，server 把溢出计数上报到 C API，
   GUI 弹「染色降级」提示。那是位预算问题，不是内存问题，是另一件更大的事。
   ⇒ 不要把 (ii) 承诺成「几十个晶体 + 几百个 filter 都能逐个开关」——那是两个功能，其中一个
   没有地基。

已存在、不必重建的地基：Colors 面板的显隐本来就是 display-time 的，不触发重算——`RenderConsumer`
给每个 color class 分一条 W×H 的 Y 通道，合成时按显隐取子集重合成，隐藏亮类后
`ParticipatingExposureScale()` 会当场重新提亮剩余暗类；
晶体身份早就在 component 的键里（CPU 侧 `ColorGateEntry`、GPU 侧 `ComponentTableEntry`
的键都含 `crystal_id`），「按晶体分桶」是现成键的一个投影，不需要新的追踪机制。
唯一的缺口是这些通道只有 Y：Colors 给每类指派色相、拿 Y 当亮度，够用；「在普通渲染里减掉
一个晶体」要的是真实颜色被移除，Y 给不了。

### 4.2 五条路线（⛔ 搁置中，重启时读）

| 路线 | 放弃哪条性质 | 内存 | 延迟 | 精确性 | 桶数上限 | GPU |
|---|---|---|---|---|---|---|
| **A 自适应分辨率网格** | 局部分辨率 | 约 4–5× 节省 | 即时 | 近似（可控） | 无硬限 | 友好 |
| **B = top-K（K=1）** | 尾部精确性 | O(1) | 即时 | 主导处精确 | 无 | 难 |
| **C top-K（K=4 等）** | 尾部精确性 | O(1)，更大 | 即时 | 由覆盖率决定 | 无 | 难 |
| **E 按需重跑单桶** | 即时性（换 1/N 算力） | O(1) | 约 1/N 次仿真 | 精确 | 无 | 无新机制 |
| **F 按物理结构选表达** | 非对称桶的精确性 | 极小 | 即时 | 对称桶精确 | 无 | 友好 |

**五条不互斥**：A 削单桶成本、C 削桶数依赖、E 用算力换内存、F 对特定桶类降维——
四个不同的轴，可以相乘。重启时不要当成五选一。

各路线的关键约束，一条一句：

- **A**：划算的形态是全体桶**共享一张**索引网格（1024² 的 uint32 索引图约 4 MB，只付一次），
  每桶只存各网格单元的 XYZ，写入是一次平坦间接、GPU 友好。坑：网格要按「哪里有结构」建，
  而这要跑了才知道 ⇒ 早期批次粗跑定网格后冻结；细分一个已攒能量的粗单元时能量只能均分给
  子单元，**误差正比于细分前攒的能量 ⇒ 必须早分**；有损，判据须保守。
- **B / C**：owner 提的「每像素存 XYZ 再附一个来源 id」就是 K=1 的 top-K。误差形态比看上去
  温和：关掉桶 A，在 A 主导的像素上减得精确（那正是 A 自己的弧），在 A 只是小贡献处减不掉 ⇒
  视觉上「弧消失，残留微弱底噪」。**失效是渐变而非崩塌**。
- **E**（可能最干净）：前提已核实——设备上每条光线的随机流按「(seed, 全局光线序号)」寻址
  （`src/core/backend/trace_backend.hpp` 的接口注释），不是按抽取顺序；而每个晶体分到的是
  一段连续序号。⇒ 用完全相同的 config 再跑一遍、只追踪晶体 k，k 拿到的是与完整运行中一模一样
  的那批光线，于是「隐藏 k 的结果 = 总图 − 单独跑出的 k 的图」，精确到补偿求和的浮点噪声
  （⛔ 不声称逐位相同）。不是压缩数据，是根本不存。量级示例：40 晶体、完整运行 60 秒 ⇒
  单桶约 1.5 秒。⚠️ **成败点未核实**：多次散射续层重采样之后，各晶体的光线序号是否仍与其他
  晶体的开关状态解耦。另：各后端的 reset 行为本就不对称（Metal 每 batch 重跑、CUDA 由 guard 只跑一次），三后端对齐
  这条不变量不是零成本。
- **F**（投机，**未核实**）：均匀朝向的晶体贡献绕太阳旋转对称 ⇒ 通道本质是散射角的一元函数，
  2048 bin 的一维剖面约 8 KB，而非一整张图的 12 MB 量级。它打的正是「random orientation 覆盖
  全天」这种最坏情况——那类桶恰恰维度最低；定向晶体产生局部特征，走 A 或 C。⛔ 两处未核实：
  「完全随机朝向」能否从配置 a-priori 判定（朝向分布只有 mean / std + 分布类型）；旋转对称在
  多次散射之后是否还成立。悬崖在「几乎对称但不完全对称」的桶——误判即丢结构，须有保守判据 +
  回落通用表达。

### 4.3 两条被否决的方向（⛔ 勿重提）

1. **用图像 codec 压缩累加通道** —— owner 提出后自行否决，理由已核实：通道是**活的累加器**
   （`AccumulateColorClassLanes` 里逐光线随机散射写 `lane_y_[c][pidx] += y`），codec 适合压
   不变的图像。块压缩格式理论上可随机寻址，但「解块→加→重编码」让同一块在一次运行里被反复
   量化上千次，误差累积是灾难，而且在每条光线的热路径上。只读的快照侧压得动，但两侧都是
   N×W×H ⇒ **天花板是省一半，不是量级改善**。另一条独立否证：若每帧都「解码一层、加一层」，
   就是 40 层 × 1024² / 帧；缓存合成结果、只在开关时重算可解，但运行中每次快照都让缓存失效 ⇒
   同样只在运行结束后可用。
2. **稀疏表达（tile 分页）** —— owner 否决，理由已核实：**很多晕是弥散的**（random orientation
   的晕几乎覆盖全天），即使能量集中在小区域，其余区域仍非零；稀疏性要的是零，这里没有。
   ⭐ 但这条否决恰好画出了 A 的形状：稀疏要**零**，自适应分辨率要**平滑**；弥散 = 低空间频率
   ⇒ 否定稀疏性的理由正是 A 成立的理由。两者互补，不是同一条路。

### 4.4 重启条件与重启时先做什么

**那个必须先问的产品问题**：「开关某条弧」是解法，「想知道哪道弧是谁做的」可能才是目的。
(i) 已经按目的做了那一半；剩下的一半是：

> 有了分析面板 + 「排除此光路 → 重跑」之后，还需要**即时**开关某条弧吗？

**重启条件**：真实用户拿着面板和「排除 → 重跑」用过之后，仍明确需要不必重跑、所见即所得的
即时开关。若答「重跑可以接受」，(ii) 整个消失。这个访谈**尚未进行**。访谈时问目的，不问解法。

若技术侧重启，只有三条便宜探针值得先跑（原先设想的稀疏度 / tile 占用 / 压缩比三项已随稀疏
路线否决而作废）：

1. **多次散射续层之后各晶体随机流是否仍解耦** —— E 的成败点，白盒读码 + 一个对照实验即可定。
2. **单桶通道的空间频谱**（不是稀疏度）—— 决定 A 能省多少。
3. **top-K 能量覆盖率（K = 2 / 4 / 8）** —— 决定 C；owner 预判「K 可能要很大」，这条探针就是
   去证实或证伪这个预判。

(ii) 若将来要放 UI，住处有一条已知约束：按 GUI 形态内测的结论，**即时开关**的控件必须与要对比
的画面同屏可见（见 [`gui-layout-architecture.md`](gui-layout-architecture.md) §8）。(i) 的面板不是
即时开关，只要求窗口不遮住预览。另：晶体的「启用 / 停用」开关是「排除后重跑」，不是 (ii)；
它与 (i) 的「排除此光路 → 重跑」属同一语义家族。

## 5. (i) 路线的继续深入（中近期）

(i) 交付后搜集了用户反馈，据此决定沿 (i) 这条路继续深入。本节列的方向**都还没有落地**，但都建在 (i) 已有的
地基上，落地可行性大，是中近期目标。

### 5.1 选定光路后的三功能（fiber 详情 / 单光路全天图 / 预设点）

**需求源起**：在分析面板里点一条光路（例如 `3-5-6-7`），看到光线在晶体里**实际**怎么走；再看
每一段之后剩下的能量占比如何逐段下降。2026-09-27 owner 与主 session 的跨仓讨论把这个需求扩成了
「选定一条光路之后」的三功能规划，并厘清了它与 [Lumice Integral](https://github.com/LoveDaisy/Lumice-Integral)
（下称 LI）Phase II 的对应关系。

#### 5.1.0 owner 的三功能规划

已有功能（(i) 识别面板、排除该光路 → 重跑，见 §3）保持不变。在其之上：

1. **光路详情**：用户选定一条光路后，展示该光路的一维姿态族（fiber）上的晶体姿态、晶体内的
   真实光路轨迹（可视化 / 动画，例如滑杆沿 fiber 扫动），以及沿光路逐段衰减的能量分配
   （beam tube 是其一种可视化形式）。
2. **单光路全天亮度图**：选定光路后，展示「单独这条光路」在全天的亮度分布，并允许在这张图上
   重新选点，回到功能 1 看新点上的姿态与光路。产品形态见 §5.1.8。
3. **预设点**：最亮点；临界点 / 线（例如切弧边缘，对应 `D_P` 的极值 / 鞍点 / 可行域边界）；
   波长相关的临界点（例如某方向上蓝光已全反射而红光仍可透过，晕的颜色在此变化）。

多次散射链：**需要**支持（组合方式见 5.1.5）。「why the halo is here」：owner 希望给用户这种
insight，产品形态见 5.1.3。

#### 5.1.1 真实轨迹是一族而不是一条

固定光源方向、出射方向与光路后，满足条件的姿态不是单个值，而是一维的姿态族（fiber）；每个
姿态下，入射面上的有效入射点构成一个多边形（beam 截面）。沿着 fiber 走，轨迹形状与逐段
Fresnel 能量占比都在连续变化——这是三个功能共同站立的结构事实：功能 1 展示的正是沿一条 fiber
的这族变化。

#### 5.1.2 三功能 ↔ S² `D_P` 场对应表

LI Phase II 把光路上所有权重对姿态的依赖收拢成一个方向（光源在晶体坐标系中的方向，由晶体姿态与光源方向共同决定），把
积分搬到球面 S² 上；像素亮度就是偏折角场 `D_P` 在某个水平集（等偏折角的曲线）上的线积分。
细节见 LI 的 [phase2 文档](https://github.com/LoveDaisy/Lumice-Integral/blob/main/docs/phase2_zh.md)，
本文不复述公式。三个功能是同一个 `D_P` 场的三种读法：

| 功能 | 在 S² 上是什么 | LI 现状（2026-09-27） |
|---|---|---|
| 2 单光路全天图 | 带求和：S² 上的事件按偏折角散射到像素 | 已投入生产（单层、以单波长为主） |
| 1 点选看 fiber | 该像素对应的水平集；带求和里落进该像素的事件就是离散化的 fiber（带权重） | 水平集提取已有；「点选 → 事件回查」未做 |
| 3 预设点 | 最亮点 = 单光路全天图的极大；临界线 = `D_P` 的临界点（极值 / 鞍点）与可行域边界（全反射起点、面可见性）；波长临界 = 可行域边界随波长（折射率随波长变化）移动 | `dp_field` / `focusing.classify` 已能分类机制（有限跳变 / 对数发散 / 弥散）；多波长在 LI backlog |

三者共享同一份数据：按「晶体 × 光路 × 波长」算一次 S² 场，**与光源方向（太阳高度）无关**，
换太阳不必重建。

#### 5.1.3 「why the halo is here」= 预设点 + 机制标签

每个预设点是 `D_P` 场上的一个结构特征，并带一条机制标签（例如「此处偏折角取极值 ⇒ 边缘锐利」
「此处蓝光已全反射、红光仍透过 ⇒ 颜色在此变化」）。用户点一个预设点，看到该点对应的姿态与光路，
就得到了解释——这是功能 3 的产品形态，也是 owner 想要给用户的 insight 的落点。

#### 5.1.4 已否决：存储回放路线

竞品 HaloPoint 的做法（owner 经验猜测，未核实）是仿真时存下若干条追踪过的光线，分析时回放。
**这条路线在功能 2 的「重新选点」交互下不成立**：每条链水库抽样 K 条光线只能回答「这条链在分析
区域里的样子」；要支持任意选点，需要按「链 × 天空位置」存储，正是会爆炸的维度。⇒ 走即时计算
（计算换存储）：给定光源方向、出射方向与光路，反解出实现该方向映射的晶体姿态，再据此画出几何
轨迹——LI 做的正是这类反解（确定性地求出实现给定映射的全部晶体姿态，而不是蒙特卡洛采样）。
⛔ **勿重提存储回放路线，除非功能 2 被砍。** 给 LI Phase I 提供仿真种子的好处，在 Phase II 路线
下价值不大。

#### 5.1.5 多次散射的组合方式与 filter 重跑退路

多次散射链：**需要**支持，是第二期。单层是 LI Phase II 的全部结构；两层链经由中间方向组合——
全天图等于对中间方向积分两层各自的单层结果（S² 仓库与光源无关 ⇒ 第二层可以直接以中间方向为
「光源」复用第一层的工具）。点选交互下，fiber 变成 4 维族（中间方向 2 维 + 各层姿态各 1 维），
可先定中间方向（例如取贡献最大者）再逐层用单层工具展示。

LI 的非目标是多次散射**场景渲染**；组合发生在消费层，具体由 LI 承担还是由 Lumice 侧组合，
待定——不再照搬「LI 不能用于跨层链轨迹」这句绝对表述。

通用退路（任意层数、任意晶体，已有，不依赖上面任何裁定）：Lumice 现有 filter「只保留选中链 →
重跑 MC」即可得该链的全天图（有噪声）。

#### 5.1.6 计算落点：按模块成熟度移植

功能 1–3 会用到 LI Phase II 的大部分内核；LI 是 Python/JAX，Lumice GUI 是 C++ 分发应用。此前
列过三条候选背景：**(a)** Lumice 内 C++ 重写（两份同语义实现，两侧单边修改持续累积偏差）；
**(b)** LI 作为 sidecar 服务（需要给终端用户分发 JAX 运行时，重，不取）；**(c)** 把 LI Phase II
内核抽成可移植 C++ 核心，LI 的 Python 侧经 binding 调用。下面的裁定把 (a)/(c) 的分歧吸收为
**时机**问题——(c) 的形态保留为移植后的终态候选，而不是现在就要在 (a)/(c) 之间选一个。

**2026-09-27 owner 裁定：计算落点不是一次性的「单实现 vs 双实现」架构选择，而是按模块成熟度
决定何时移植。**

1. **现在不移植**：全部留在 LI 的 JAX 实现里，研究与写作自由改动。
2. **移植触发** = 两个条件同时满足：面板功能真正排期；该模块一段时间无语义改动（参考：
   晶体泛化阶段 2、多波长、上下不对称锥都已落地之后）。
3. **移植后**：JAX 是权威、C++ 是派生实现，由 parity fixture 锁定（路径拓扑：无内反射 / 含
   内反射 / 锥晶族外 × 点类别：随机 / 临界点 / 近边界；模板取 LI 侧 `compare_*.py` 的形状），
   CI 运行；改动单向流动——先改 JAX → parity 红 → 再改 C++。这不是两份对等实现静默分叉，
   分叉被自动检出、没有「哪边是对的」之问。
4. **功能 1/2 与功能 3 同样处理**（`band_sum`/`s2_store` 与功能 3 的模块一样年轻）；C++ 侧
   采用前向 hyper-dual 模板做标量求导，不引入 AD 框架。
5. 某模块长期稳定后，是否让 LI 也改调 C++ 并退役 JAX 版——答案见下方「仓库定位」一段：
   按角色 + 共享判据，算法层是，原语层否。

**实测依据**（LI 仓 explore `panel-inverse-probe` / `ad-port-probe`；细节见 LI
[`docs/overview.md`](https://github.com/LoveDaisy/Lumice-Integral/blob/main/docs/overview.md) §5.3，
本文不复制）：面板精度下算力充裕——161×81 窗口 N=1e6 全链路 3.4 s、单像素取 fiber 1–2 ms
（Python 渲染约 74 µs/px，512² 全天图约 20 s）；功能 1/2 核心（`band_sum`/`s2_store`/`weights`/
`geometry`）零 JAX；功能 3 的 AD 可由 C++ 前向 hyper-dual 模板（`Jet2<3>`，约 150 行零依赖）
精确复现，3 条路径（含内反射、锥晶 `13-15-26-28`）对 JAX 值/梯度/Hessian 相对误差 ≤1e-11，
单点 C++ 193 ns vs JAX 104 µs；功能 3 的 C++ 估 2800–3600 行，大头是边界 / 水平集 walk 状态机
而非 AD。修史实测（git log）：相关模块都很年轻且仍在研究驱动下变化——`dp_field`/`contour`/
`focusing` 仅 2–3 天历史，`optics.py` 12 天 16 次提交（部分反射语义重写、法向改读晶体），
`band_sum`/`s2_store` 4 天 25 次；已知还要落地的改动（晶体泛化阶段 2 `G_true`、上下不对称锥、
多波长、多次散射组合）都会打到同一批文件——这是「现在不移植」的直接依据。

**仓库定位（2026-09-28 owner 裁定）**：Lumice 与 LI 的分工原先隐含地按「正向 MC / 逆向确定性
积分」划分，这其实是三个维度（数值方法、角色、运行时）碰巧重合。光路分析升级为 Lumice 第二产品
核心之后，引入了「逆向方法 + 产品角色」这一新组合（见 §5.1.8）——按数值方法划分就此失效，按
**角色**划分仍然成立，替代原先的二元划分：

- **Lumice = 产品**：用户能用到的全部计算都在这里，C++，每个语义只有一份产品实现——包括光路
  分析在运行时要用的逆向能力（单光路反解与 fiber、S² 场、带求和、临界点分类）。
- **LI = 研究与参照**：新方法诞生的地方、数学规格与写作系列的支撑，同时是 Lumice 的独立校验
  对象；LI 的既有非目标不变（不做产品 GUI、不做多次散射场景渲染）。

共享判据不是单纯的「稳定就共享」，而是**「稳定，且不是两边互相校验的对象」**：按「稳定」这一条，
最先进共享库的会是原语层（晶体几何、Snell / Fresnel、对称约化），而原语层恰恰是两边各自实现
最有价值的地方——2026-09-27 Lumice `Crystal::MakePrismClosedForm` / `MakePyramidClosedForm`
把 `fn_period_` 硬编码为 6、不读 `face_distance` 的缺陷，正是 LI 用独立实现对照才抓出来的
（已由 PR #429 修复）。⚠️ 这条实证**专指光路分析面板的物理分组**（`raypath-symmetry.md` §1.1 的
L2，`SymmetrySemantics::kPhysical`）——对 filter（以及染色 ref）而言，六方标号规约、周期恒为 6
正是 L1（`kLabel`）的本意；PR #429/#430 当时顺带把 filter 的约化也改成按形状读周期，这一半已被
owner 判定为误伤 L1 语义，由 PR #436 恢复（`fix(core): a filter's P/B/D is a label equivalence
again`）。实证发现本身仍然成立——LI 当时对照的正是面板行（L2）的口径，不因 filter 那半的回退而
失效。反面证据是同一轮里对称约化在两个仓库各做了一遍（LI 的 `G_true`，本仓 PR #429–#431）：那一轮
里本仓 filter 曾短暂跟面板一起改用 L2，PR #436 之后本仓 filter 回到 L1、面板保持 L2——两边共用
一份原语，这类缺陷会让两边一起错而不可见。因此按层处理：

- **原语与约定层**（晶体几何、面编号、对称约化、Snell / Fresnel）：两边刻意各留一份，作为互相
  校验的对象；用 parity / 约定测试锁定。它们变化慢，两份的成本低。
- **算法层**（单光路反解与 fiber 行走、S² 场、带求和、临界点分类）：还年轻、仍在研究驱动下
  变化时，两边各自实现（即上面 5.1.6 现行做法：JAX 先改、C++ 跟随、parity fixture 锁定）；
  成熟之后收敛为 Lumice 的一份 C++ 实现，经 Lumice 共享库给 LI 使用，LI 那份 JAX 版在 LI 不再
  研究该模块时退役。

**两仓计算用的对称性口径（2026-09-28）**：上面「原语与约定层刻意各留一份」对对称约化这一项
需要更精确的对应——两仓、两个消费者，各自用的其实是 `raypath-symmetry.md` §1.1「Two Meanings
of One Bit Set」定义的两种口径中的一种，而不是同一口径的两份独立实现：

- Lumice filter（以及染色 ref）的 P/B/D = **L1 标号等价**（`SymmetrySemantics::kLabel`）：不看
  形状、不看取向分布，六方标号规约、周期恒为 6；
- Lumice 光路分析面板的行 = **L2 物理等价**（`SymmetrySemantics::kPhysical`，
  `DeriveSymmetryGating(kPhysical)`）：形状（§2a）与取向集体（§2b）两个条件都成立才合并；
- LI 的 `G_true`（`symmetry/crystal_group.py`）= L2 的形状那一半（姿态那一半由调用方的姿态分布决定），
  与面板同口径；LI 的 L1 标号轨道是 `symmetry/reflection_group.py` 的 `pbd_orbit`，与 filter 同口径。
  ⚠️ LI 的 `path_class.g_true_orbit`（原名 `pbd_orbit_hexprism`，已改名，旧名保留为弃用别名）——旧名里带 PBD，但实际按所给晶体的 `G_true` 展开，是 **L2**；
  只在正六棱柱（`G_true` = 整个 D6h）上恰好等于 L1。即 LI 内部也同时维护两种口径，两仓四份实现按
  口径两两对应，不是「LI 一份、Lumice 一份」；
- 即将发布的 `liblumice_analytic`（本节候选的第一个共享模块）只接受具体的面序列，不带对称参数、
  不提供约化接口——对称约化属于原语与约定层，两仓各留一份、互为校验对象，不经共享库分发。调用方
  若要在这层接口之外自行做约化，必须说明用的是哪种口径；LI ↔ Lumice 的 parity fixture 命名同样
  要标明口径，否则两个都合理但不同的约化会被当成同一件事对照，产生假红或假绿；
- 典型分叉：三重对称的晶体（如 `face_distance` 交替的三重棱柱）——L1 按六重标号合并（filter 的
  P 总是这样做，见 §1.1），L2 只按三重物理对称合并（近面与远面能量不同，不可合并）；同一份
  `.lmc` 用两种口径读，得到的光路类数量不同。

共享的载体是 Lumice 正式发布的共享库，LI 经 Python binding 使用。这是 Lumice 共享库的第一个
正式需求（第一个外部消费者），触发了 [`api-layering-and-product-lines.md`](api-layering-and-product-lines.md)
所记的两个触发信号「准备正式发布动态库」与「第二条产品线立项」——且该文顺序约束（产品线先决定 API
形状，发布才冻结 API）此时第一次被满足：光路分析的形态已定稿（§5.1.8），第一个外部消费者也已
明确；细节见该文新增的一节。第一个候选模块是单光路反解 + fiber 行走——语义稳定（LI Phase I
已于 2026-09-23 收官）、体量小、且 Analyze 一期本来就要在 C++ 里实现它（§5.1.8）。这部分已
立项为本仓一个 scrum（尚未推进，owner 会先审阅其拆分）。

#### 5.1.8 产品形态

**2026-09-27 owner 裁定**：光路分析升级为 Lumice 的**第二产品核心**，与渲染并列——点击
Analyze 后出现与主窗口同级大小的界面，不是嵌在预览旁的一块面板。

**Analyze 窗口彻底重新设计**：不以现有 (i) 面板为基础改造。(i) 已交付的能力——专用分析运行、
完整链 id、锥形分析区域、能量份额表（§3、§5.2）——作为地基复用，但界面不沿用。

**窗口内自成闭环，不依赖主预览**（2026-09-28 owner 定稿，D1–D9）：窗口内固定两块区域，各自
只有一种点击语义——**场景全景**（MC 渲染的场景总亮度，点击 / 拖动 = 设锥形分析中心）与
**光路视图**（单独选中光路的亮度分布，点击 = 放 / 移观察点）（D1）。拆成两张图的理由：原「一张
全天图」方案里同一个点同时是锥形中心（决定列表）和 fiber 查询点（决定可视化），选中光路后再点
别处会产生两种互相矛盾的预期；拆成两张图，各自只有一种点击语义，歧义从结构上消失。闭环路径：

> 场景全景上点一点 → 以该方向为中心的锥形分析 → 光路列表 → 选中一行 → 光路视图显示这条光路
> 单独的亮度分布 + 预设点标记，场景全景叠一条**只读**轮廓标出该光路在天空中的范围 → 拖动 /
> 点击光路视图上的观察点（自动吸附到该光路的可达区域）→ 太阳方向球、晶体内光路动画、详情区
> 随观察点 / fiber 位置联动。

**投影：单圆盘等面积，不用 dual equal-area 2:1**（D2，owner 目视确认）：两张图都用单个圆盘的
等面积投影（Lambert 方位等面积，中心可在球面任意方向），不用 GUI 主窗口的 dual equal-area 2:1
双圆盘——原型实测该布局横向稀缺、纵向富余：2:1 双圆盘让每个半球只得列宽的一半（1440×860 窗口下
一个半球直径约 175 px，单圆盘约 350 px），且下方纵向空间不再空置。场景全景默认上半球，提供
上 / 下半球切换，不提供整球。

**光路视图的地图式交互**（D3，owner 提议 + 原型验证）：拖动 = 平移，滚轮 = 缩放（视图半径从
全天到约 1.5°）；「Fit」与「Full sky」按钮。选中光路时自动 Fit：框住这条光路；若它由多个分离
光斑组成（例如左右幻日），框住观察点所在的那一个。点击放观察点，并吸附到该光路的可达区域
（点在光路够不到的地方时移到最近的可达点）——这是「只能在可行区域的采样点之间拖动」的轻量
实现，无需额外点阵 UI。缩放后的像按视图分辨率重新求值，不是把低分辨率天空图放大：一期对这一条
光路按视图重跑 MC，二期 LI 按视图分辨率确定性求值——这是缩放的真实代价，要在实现里体现。太阳
高度等场景变化后，若用户没有手动平移 / 缩放过，光路视图自动重新 Fit。

**姿态可视化 = 晶体系中的太阳方向球**（D4，owner：「比我想的要好得多」）：取代原先设想的 SO(3)
可视化 / 截面图。球面上画：偏折角场 `D_P`（着色）、该光路不可行的区域（标出）、观察点对应偏折角
的水平集——水平集就是 fiber；fiber 按姿态分布权重着色，下方一条「沿 fiber 权重条」+ 滑杆 +
播放。交互：沿水平集拖动 = 出射方向不变、只改姿态（即 fiber 滑杆）；横跨水平集拖动 = 出射方向
改变，光路视图上的观察点随动。三处（光路视图 / 太阳方向球 / 光路 3D）共享同一个观察点，双向
联动。定向晶体（plate / 水平柱）下，权重只在水平集上少数几处非零——这就是「维度坍缩」的直观
呈现；随机取向时权重沿整条 fiber 分布。面法向（1–8）标在球面上，入射面 / 出射面区分着色；
`D_P` 的极值点标在球面上。

⚠️ assistant 推断，待与 LI 核对：「fiber ↔ 水平集一一对应」在锥晶与含内反射的光路上是否仍成立。

> ✅ **核验（2026-09-29，本仓 `Lumice raypath` + analytic 核，未调用 LI）**：上面这条在棱柱 `3-5`、含内反射
> `3-5-6-7`、锥晶 `13-15-26-28` 上成立（|R·u+s| ≤ 3e-15，|out−T| ≤ 4.5e-12）。退化的不是「等值线=纤维」，
> 而是「纤维 ∩ 姿态族」：纬线不变的光路（如 `3-6-4-8`）等值线是纬线圈、纤维是被有效域截断的圆弧，
> 片晶族可整族落到天空一点。逐点核验用的是 `raypath` 输出的 `points[*].sun_in_crystal` 与 `outgoing_direction`；
> 字段层面的读法见 `doc/raypath-cli-output.md` §3.10。柱晶 / Parry / Lowitz 族只在 `3-5` 上验过（与纤维交于位姿空间的离散点，
> 判据在位姿空间，u 球投影带必要非充分）；LI 另发现 Parry 族对折叠矩阵为 `S_x` 的光路（如 `1-6-2`）也会整族坍缩。
> **与 LI 的对照（LI PR #43，`fa8dadd`，两条链路实现互不共享）**：D4 在三类晶体上一致成立；退化判定一致（LI 的机械判据：
> c 轴约束族、楔角 0、折叠矩阵与绕 c 轴旋转可交换，`focusing.family_pinned`）；「有等值线而无纤维」一致（LI `gated_out`
> ↔ 本仓 `reach` 空态三分）。

**机制标签词表：以 LI 全集为契约**（D7，事实更正，来自 LI 源码）：LI `focusing` 模块
（`src/lumice_integral/focusing.py` 模块文档串）实际的随机取向 profile 有 8 种：`finite_jump`
（有限跳变）、`log_divergence`（对数发散）、`inverse_sqrt_divergence`（反平方根发散）、
`cone_point`（锥点）、`crease`（折痕）、`boundary_onset`（边界起点）、`degenerate`（退化）、
`point_mass`（点质量）；此外还有一条正交的轴：雅可比聚焦（来自 `D_P` 场本身）vs **维度坍缩**
（来自姿态分布把姿态限制在低维族上）。接口契约应覆盖全集与两条轴；维度坍缩是 Lumice 最常见
场景（水平板、Parry 等定向晶体）里亮特征的主要来源，缺了它机制卡片在这些场景里说不出东西。
机制卡片 = 术语 + 一句话解释 + 小示意图（该位置附近偏折角随姿态的剖面）。示例：

- **有限跳变**：内部非退化极值 ⇒ 锐边、亮度台阶。
- **对数发散**：鞍点 ⇒ 弱峰，易被邻近边界起点淹没。
- **边界起点**：可行域边界（全反射起点 / 面可见性）⇒ 拐角。

标签词表的权威来源仍是 LI `focusing` 的分类（见 5.1.2 引用的 phase2 文档），作为 LI↔Lumice
接口契约固定，不在 Lumice 侧另造一套命名。

**两期（2026-09-28 owner 修订）**：原两期划分是一期 = 骨架 + MC 部分、fiber / 姿态 / 3D 全在
二期，依据是「只有 LI 能反解」——这个前提被原型本身推翻：原型里的 fiber、姿态、晶体内光路都是
页内临时计算的（单层光路正向追迹一个方向只需几次折射反射；在太阳方向球上找偏折角 = δ 的点是
一维求根，再沿水平集走；有了太阳方向和出射方向，两组正交基唯一定出姿态），拖动时每帧重算。

新划分：**一期** = 工作区骨架 + 场景全景 + 锥形分析 + 光路列表 + 光路视图（MC，按视图重跑该
光路）+ **单光路反解与 fiber 行走（Lumice C++，parity 对照 LI，见 §5.1.6「仓库定位」）**驱动的
太阳方向球、fiber 滑杆与播放、光路 3D、详情区点级信息；**二期** = LI 算法模块成熟移植后接入：
确定性单光路图（「解析结果」）、临界点分类、机制卡片、除「最亮点」之外的预设点、波长临界。
Analyze 窗口正式排期即满足 §5.1.6 移植触发的第一个条件（「面板功能真正排期」）。

> 一期「选定光路之后」的计算已由 `Lumice raypath` 子命令与其背后的单光路分析模块
> （`src/raypath/`，C API `LUMICE_AnalyzeSinglePath`）提供，界面复用同一模块与同一份 JSON
> （字段见 `doc/raypath-cli-output.md`，用法见 `doc/user-manual/03-cli-quickstart.md`）。

**窗口关系与场景同步（2026-09-27 owner 裁定）**：

- **Render / Analyze 是同一窗口下的两个工作区**，顶部标签切换（不是两个独立系统窗口）：共享同一份
  场景文档，状态管理简单，单屏笔记本也放得下。
- **场景变更后自动重算**，成本靠「只有当前显示的工作区在算」控制：
  - 在 Render 工作区改场景时，Analyze 不计算，只标记已过时；切回 Analyze 时再算（惰性）。
  - 在 Analyze 工作区改场景时，沿用 Render 已有的去抖重提交，取消在跑的分析；旧结果变暗保留，
    新结果随增量 MC 逐步收敛后替换。
  - 二期的确定性部分：S² 场与光源无关，改太阳高度只需重新散射（秒级以内）；改晶体 / 光路 /
    波长才重建（面板精度下每条光路约秒级），按「晶体 × 光路 × 波长」缓存。
  - 兜底：单次重算超过阈值时显示进度，旧结果继续可用。

### 5.2 (i) 面板的四个机制级升级点

这四项与 (i) 的实现细节绑在一起，正文与各自的触发条件都在
[`raypath-analysis-panel.md`](raypath-analysis-panel.md) §8，这里只列名字：

| 升级点 | 一句话触发条件 |
|---|---|
| GPU 直方图 kernel | 分析已绑定在线光线分配之后，仍有场景在 CPU 池上等待过久，且 GPU 回传 per-ray 记录的代价被证明值得 |
| 密度排序（能量 / 覆盖立体角） | 用户明确反馈「总能量降序」把弥散但总量大的链排到了不该靠前的位置 |
| 列表 → 预览高亮联动 | 用户需要「选中一行就在画面上看到它亮在哪」，而不止是数字；被 Analyze 工作区的光路视图 + 场景全景只读轮廓吸收（§5.1.8） |
| 多段链排除 | filter 模型本身获得跨层链的表达能力 |

⛔ GPU 直方图若将来要做，不得走「恢复 `ReadbackExitRays` 逐记录读回」的路——device-fused 单引擎
有意删掉了它；可行的形状是设备上携带跨层链键 + 设备侧直方图哈希表，Metal / CUDA 各一份外加
parity，是多子任务量级。单核时代（GPU 偏好 server 上分析曾只有 1 个 worker）测得的等待时间不构成
触发证据。

## 6. 共用地基

上面这些方向共享同一块地基，这也是 (i) 先行的另一个回报：

- **完整链 id**：每条光线携带一个跨多次散射层的链 id，经 interning 表逐段约化，
  回答「这条光线走的是哪条完整光路」。
- **专用分析运行**：一次不渲染、只做统计的运行，与渲染提交共用同一份场景编码。
- **CPU 路**：分析运行显式只走 CPU，所以在它上面加 per-ray 数据不必同步改 Metal / CUDA。

选定光路后的三功能（§5.1）另需一块新地基：按晶体 × 光路 × 波长的 S² `D_P` 场（与光源无关，
可缓存）——这块地基今天不存在，计算落点按模块成熟度决定移植时机，以及两仓按角色划分、共享
判据见 §5.1.6。

新方向要做的，是在这块地基上**多带一点东西**：轨迹 + 分段能量要每次命中面的能量（§5.1），
密度排序要每条链的粗天球覆盖，高亮联动要按需回答「这条链落在哪些像素」。(ii) 则是唯一**不**建在
这块地基上的方向——它要的是每桶一张图，这正是地基刻意拆掉的那个维度。
