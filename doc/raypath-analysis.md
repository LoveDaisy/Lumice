## 1. 功能全景

「光路分析」这个词覆盖的是一族用户问题，它们共享一个对象（光线从光源到相机所经过的
完整光路），但要回答的问题、需要的数据形状、以及成本，彼此差别很大：

- **这道弧是谁做的？** —— 天空某处的光由哪些光路贡献、各占多少。
- **关掉它，下面压着什么？** —— 在普通渲染图上把某个晶体 / 某条光路的贡献即时去掉，
  看剩下的画面。
- **光在晶体里实际怎么走？每一段剩多少能量？** —— 点一条光路（如 `3-5-6-7`），看到它在晶体
  里的真实轨迹，以及能量沿路径逐段衰减的比例。

前两个问题是内测用户最早提出的需求拆开后的两半，第三个是后来的用户诉求。状态总表：

| 方向 | 状态 | 依赖的地基能力 | 详见 |
|---|---|---|---|
| **(i) 识别**：列出一个区域里各光路成分与占比 | ✅ 已交付（PR #347） | 完整链 id、专用分析运行、CPU 路 | §3；[`raypath-analysis-panel.md`](raypath-analysis-panel.md) |
| **(ii) 剥离**：在渲染图上即时开关某个桶 | ⏸ 搁置（owner 2026-08-26 裁定） | 每桶真实辐射量（内存墙所在） | §4 |
| **真实光路轨迹 + 分段能量占比** | 🔜 中近期，未落地，可行性大 | 完整链 id、专用分析运行、晶体几何 | §5.1 |
| (i) 面板的四个机制级升级点 | 🔜 各有触发条件，未触发 | 同 (i) | §5.2；[`raypath-analysis-panel.md`](raypath-analysis-panel.md) §8 |

## 2. 拆分决策：(i) 识别 vs (ii) 剥离

内测用户最初提的是「在普通仿真图上动态开关某个晶体 / 某个 filter 对应的弧」。
拆开看是两个需求，成本落在完全不同的地方：

| | 用户要回答的问题 | 需要什么 | 成本量级 |
|---|---|---|---|
| **(i) 识别** | 「这道弧是谁做的」 | 各贡献者的**份额**（最初设想是每像素一个主贡献者 id） | 与桶数无关（一张 uint16 id 图在 1024² 下约 2 MB；已交付形态更小，见 §3） |
| **(ii) 剥离** | 「关掉这道亮的，看下面压着什么」 | 每桶**真实辐射量** | 与桶数**线性**：XYZ 每桶在 1024² 下约 24 MB（含快照影子一份） |

**为什么先做 (i)**：

1. (i) 的成本与桶数无关，(ii) 的成本随桶数线性增长并且撞墙（§4.1）。
2. 「开关某条弧」是用户提出的**解法**，「知道这里有什么、各占多少」才可能是他们的**目的**。
   两者不一定是同一件事，而它们的成本差一个量级。按目的做，(i) 就够回答大半问题；
   (ii) 剩下的只是「是否还需要**即时**开关」这一窄问题（§4.4）。
3. 在 (i) 之上顺带就有一条 (ii) 的部分解：列表行 →「排除此光路」→ 生成 filter → 重跑。
   零新增存储，代价是等一次重跑而不是即时。

## 3. (i) 已交付的形态

(i) 没有按最初设想做成「每像素一张主贡献者 id 图」，而是做成了第三种形态：
一个独立的光路分析面板，带自己的 Analyze 按钮，点击后发起一轮**专用运行**——
这轮运行**不渲染**，只按「完整光路」（从光源到相机，跨多次散射层，按对称性逐段约化）
聚合能量，按能量降序列出。分析区域三档：全天 / 画幅内 / 以某个方向为中心的锥形邻域。

它绕开内存墙的方式可以拆成两处：(ii) 的成本是 N（按光路分桶）× W×H（每桶一张图），
而「同一次运行既要出渲染图又要出分解」把这两个维度焊在一起。**专用运行**拆掉了与渲染的
耦合，**统计量而非图**拆掉了像素维度，于是内存只随「有多少条不同的光路」增长，并且已被
有界记录压成常量上界（`raypath-analysis-panel.md` §3.6）。

它也是 §4.2 路线 E「不存、需要时算回来」的泛化：E 是同一个 consumer 逐桶重跑，这里是换一个
consumer（按链 id 聚合，而不是按像素渲染）跑一次，一次拿到所有桶的排序。

v1 的四条裁决（CPU 路且显式声明、完整链、锥形 ROI、按总能量降序）、诚实边界与后续修复，
都在 [`raypath-analysis-panel.md`](raypath-analysis-panel.md)（§2 裁决、§6 诚实边界）；
用户侧怎么用见 [用户手册](user-manual/06-raypath-analysis_zh.md)。本文不复述。

## 4. (ii) 剥离：为什么搁置

⛔ **(ii) 已于 2026-08-26 由 owner 决定搁置，不是待办。** 搁置理由：五条实现路线（§4.2）各有
优点但找不到好的权衡点；top-K 看起来最均衡，但 owner 预判实际使用中用户会要求很大的 K，
内存压力仍在。更关键的是，卡住决策的不确定度**已经不是技术性的**：剩下的两个问题——用户要
多大的 K、有了光路分析之后还要不要单独开关——只有用户能答，再做多少轮设计也答不出来。

本节保留的是重新推导代价很高的部分：已核实的规模事实、五条路线的关键约束、被否决的方向。

### 4.1 两条已核实的规模事实（⛔ 勿凭印象重推）

模拟分辨率档位为 512 / 1024 / 2048 / 4096，GUI 默认 1024（`kSimResolutions`，
`src/gui/gui_state.hpp`）。每桶成本 = 累加通道 + 快照影子各一份：

| 每桶 | 1024² | 4096² |
|---|---|---|
| **Y-only**（今天 Colors 面板的形态） | 8 MB | 128 MB |
| **XYZ**（剥离需要的真实颜色） | 24 MB | 384 MB |

1. **内存墙不是 XYZ 引入的，Y-only 今天就撞得上。** 40 个晶体 × 4096 分辨率下，
   现有 Y-only 形态就是约 5 GB；XYZ 只是把同一堵墙往前挪 3 倍。真正的成本源是
   **「为每个桶预先分配一条全分辨率通道」这个形态**，不是通道里装几个分量。
   ⇒「保住 Y-only 就能支撑极端用法」不成立——那个用法今天也不成立，只是还没有人同时开几十个
   color class。
2. **「几百个 filter 逐个开关」在撞内存之前先撞位预算。** component 掩码是 64 位
   （`ComponentTable::kMaxBits = 64`），超出后溢出项拿不到位，server 把溢出计数上报到 C API，
   GUI 弹「染色降级」提示。那是位预算问题，不是内存问题，是另一件更大的事。
   ⇒ 不要把 (ii) 承诺成「几十个晶体 + 几百个 filter 都能逐个开关」——那是两个功能，其中一个
   没有地基。

已存在、不必重建的地基：Colors 面板的显隐本来就是 display-time 的，不触发重算；
晶体身份早就在 component 的键里（CPU 侧 `ColorGateEntry`、GPU 侧 `ComponentTableEntry`
的键都含 `crystal_id`），「按晶体分桶」是现成键的一个投影，不需要新的追踪机制。
唯一的缺口是这些通道只有 Y：Colors 给每类指派色相、拿 Y 当亮度，够用；「在普通渲染里减掉
一个晶体」要的是真实颜色被移除，Y 给不了。

### 4.2 五条路线（⛔ 搁置中，重启时读）

| 路线 | 放弃哪条性质 | 内存 | 延迟 | 精确性 | 桶数上限 | GPU |
|---|---|---|---|---|---|---|
| **A 自适应分辨率网格** | 局部分辨率 | 约 4–5× 节省 | 即时 | 近似（可控） | 无硬限 | 友好 |
| **B = top-K（K=1）** | 尾部精确性 | O(1) | 即时 | 主导处精确 | 无 | 难 |
| **C top-K（K=4 等）** | 尾部精确性 | O(1)，更大 | 即时 | 由覆盖率决定 | 无 | 难 |
| **E 按需重跑单桶** | 即时性（换 1/N 算力） | O(1) | 约 1/N 次仿真 | 精确 | 无 | 无新机制 |
| **F 按物理结构选表达** | 非对称桶的精确性 | 极小 | 即时 | 对称桶精确 | 无 | 友好 |

**五条不互斥**：A 削单桶成本、C 削桶数依赖、E 用算力换内存、F 对特定桶类降维——
四个不同的轴，可以相乘。重启时不要当成五选一。

各路线的关键约束，一条一句：

- **A**：划算的形态是全体桶**共享一张**索引网格（1024² 的 uint32 索引图约 4 MB，只付一次），
  每桶只存各网格单元的 XYZ，写入是一次平坦间接、GPU 友好。坑：网格要按「哪里有结构」建，
  而这要跑了才知道 ⇒ 早期批次粗跑定网格后冻结；细分一个已攒能量的粗单元时能量只能均分给
  子单元，**误差正比于细分前攒的能量 ⇒ 必须早分**；有损，判据须保守。
- **B / C**：owner 提的「每像素存 XYZ 再附一个来源 id」就是 K=1 的 top-K。误差形态比看上去
  温和：关掉桶 A，在 A 主导的像素上减得精确（那正是 A 自己的弧），在 A 只是小贡献处减不掉 ⇒
  视觉上「弧消失，残留微弱底噪」。**失效是渐变而非崩塌**。
- **E**（可能最干净）：前提已核实——设备上每条光线的随机流按「(seed, 全局光线序号)」寻址
  （`src/core/backend/trace_backend.hpp` 的接口注释），不是按抽取顺序；而每个晶体分到的是
  一段连续序号。⇒ 用完全相同的 config 再跑一遍、只追踪晶体 k，k 拿到的是与完整运行中一模一样
  的那批光线，于是「隐藏 k 的结果 = 总图 − 单独跑出的 k 的图」，精确到补偿求和的浮点噪声
  （⛔ 不声称逐位相同）。不是压缩数据，是根本不存。量级示例：40 晶体、完整运行 60 秒 ⇒
  单桶约 1.5 秒。⚠️ **成败点未核实**：多次散射续层重采样之后，各晶体的光线序号是否仍与其他
  晶体的开关状态解耦。另：各后端的 reset 行为本就不对称，三后端对齐这条不变量不是零成本。
- **F**（投机，**未核实**）：均匀朝向的晶体贡献绕太阳旋转对称 ⇒ 通道本质是散射角的一元函数，
  2048 bin 的一维剖面约 8 KB，而非一整张图的 12 MB 量级。它打的正是「random orientation 覆盖
  全天」这种最坏情况——那类桶恰恰维度最低；定向晶体产生局部特征，走 A 或 C。⛔ 两处未核实：
  「完全随机朝向」能否从配置 a-priori 判定（朝向分布只有 mean / std + 分布类型）；旋转对称在
  多次散射之后是否还成立。悬崖在「几乎对称但不完全对称」的桶——误判即丢结构，须有保守判据 +
  回落通用表达。

### 4.3 两条被否决的方向（⛔ 勿重提）

1. **用图像 codec 压缩累加通道** —— owner 提出后自行否决，理由已核实：通道是**活的累加器**
   （`AccumulateColorClassLanes` 里逐光线随机散射写 `lane_y_[c][pidx] += y`），codec 适合压
   不变的图像。块压缩格式理论上可随机寻址，但「解块→加→重编码」让同一块在一次运行里被反复
   量化上千次，误差累积是灾难，而且在每条光线的热路径上。只读的快照侧压得动，但两侧都是
   N×W×H ⇒ **天花板是省一半，不是量级改善**。另一条独立否证：若每帧都「解码一层、加一层」，
   就是 40 层 × 1024² / 帧；缓存合成结果、只在开关时重算可解，但运行中每次快照都让缓存失效 ⇒
   同样只在运行结束后可用。
2. **稀疏表达（tile 分页）** —— owner 否决，理由已核实：**很多晕是弥散的**（random orientation
   的晕几乎覆盖全天），即使能量集中在小区域，其余区域仍非零；稀疏性要的是零，这里没有。
   ⭐ 但这条否决恰好画出了 A 的形状：稀疏要**零**，自适应分辨率要**平滑**；弥散 = 低空间频率
   ⇒ 否定稀疏性的理由正是 A 成立的理由。两者互补，不是同一条路。

### 4.4 重启条件与重启时先做什么

**那个必须先问的产品问题**：「开关某条弧」是解法，「想知道哪道弧是谁做的」可能才是目的。
(i) 已经按目的做了那一半；剩下的一半是：

> 有了分析面板 + 「排除此光路 → 重跑」之后，还需要**即时**开关某条弧吗？

**重启条件**：真实用户拿着面板和「排除 → 重跑」用过之后，仍明确需要不必重跑、所见即所得的
即时开关。若答「重跑可以接受」，(ii) 整个消失。这个访谈**尚未进行**。访谈时问目的，不问解法。

若技术侧重启，只有三条便宜探针值得先跑（原先设想的稀疏度 / tile 占用 / 压缩比三项已随稀疏
路线否决而作废）：

1. **多次散射续层之后各晶体随机流是否仍解耦** —— E 的成败点，白盒读码 + 一个对照实验即可定。
2. **单桶通道的空间频谱**（不是稀疏度）—— 决定 A 能省多少。
3. **top-K 能量覆盖率（K = 2 / 4 / 8）** —— 决定 C；owner 预判「K 可能要很大」，这条探针就是
   去证实或证伪这个预判。

(ii) 若将来要放 UI，住处有一条已知约束：按 GUI 形态内测的结论，**即时开关**的控件必须与要对比
的画面同屏可见（见 [`gui-layout-architecture.md`](gui-layout-architecture.md) §8）。(i) 的面板不是
即时开关，只要求窗口不遮住预览。

## 5. (i) 路线的继续深入（中近期）

用户反馈表明 (i) 这条路是对的，决定继续深入。本节列的方向**都还没有落地**，但都建在 (i) 已有的
地基上，落地可行性大，是中近期目标。

### 5.1 真实光路轨迹 + 分段能量占比

**需求**：在分析面板里点一条光路（例如 `3-5-6-7`），看到光线在晶体里**实际**怎么走；再看每一段
之后剩下的能量占比如何逐段下降。

- **要的是真实轨迹，不是示意图。** 竞品 HaloPoint 有这个功能，用户很依赖。它的实现方式（owner
  经验猜测，未核实）是在仿真中存下若干条追踪过的光线，在分析界面重放。
- **不必照搬「存储重放」。** 另一条路是不存储、需要时即时算：给定光源方向、出射方向与光路，
  反解出实现这一方向映射的晶体姿态，再据此画出几何轨迹。
  [Lumice Integral](https://github.com/LoveDaisy/Lumice-Integral) 做的正是这类反解（确定性地求
  实现给定映射的全部晶体姿态，而不是蒙特卡洛采样），可能提供可复用的成果。这是 owner 提出的
  方向，**尚未评估**；立项前先读它的 [总览](https://github.com/LoveDaisy/Lumice-Integral/blob/main/docs/overview_zh.md)
  与 phase 文档。⚠️ 已知边界：Lumice Integral 明确把多次散射列为非目标，跨层链的轨迹不能直接
  指望它。
- **已有素材**：`LUMICE_GetCrystalMesh` 与晶体预览 FBO 已能画出晶体本身。
- **已知缺口**：分析直方图目前只记每条链**出射时的总能量**；分段能量需要每次命中面时的能量
  向量。好消息是分析运行只走 CPU 路，补这份数据不必动三后端。

### 5.2 (i) 面板的四个机制级升级点

这四项与 (i) 的实现细节绑在一起，正文与各自的触发条件都在
[`raypath-analysis-panel.md`](raypath-analysis-panel.md) §8，这里只列名字：

| 升级点 | 一句话触发条件 |
|---|---|
| GPU 直方图 kernel | 分析已绑定在线光线分配之后，仍有场景在 CPU 池上等待过久，且 GPU 回传 per-ray 记录的代价被证明值得 |
| 密度排序（能量 / 覆盖立体角） | 用户明确反馈「总能量降序」把弥散但总量大的链排到了不该靠前的位置 |
| 列表 → 预览高亮联动 | 用户需要「选中一行就在画面上看到它亮在哪」，而不止是数字 |
| 多段链排除 | filter 模型本身获得跨层链的表达能力 |

## 6. 共用地基

上面这些方向共享同一块地基，这也是 (i) 先行的另一个回报：

- **完整链 id**：每条光线携带一个跨多次散射层的链 id，经 interning 表逐段约化，
  回答「这条光线走的是哪条完整光路」。
- **专用分析运行**：一次不渲染、只做统计的运行，与渲染提交共用同一份场景编码。
- **CPU 路**：分析运行显式只走 CPU，所以在它上面加 per-ray 数据不必同步改 Metal / CUDA。

新方向要做的，是在这块地基上**多带一点东西**：轨迹 + 分段能量要每次命中面的能量（§5.1），
密度排序要每条链的粗天球覆盖，高亮联动要按需回答「这条链落在哪些像素」。(ii) 则是唯一**不**建在
这块地基上的方向——它要的是每桶一张图，这正是地基刻意拆掉的那个维度。
